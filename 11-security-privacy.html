Chapter 11 · Locking the Doors

Security & Privacy

Every chapter so far has been about getting data somewhere. This one is about controlling who else gets to see it, touch it, or reach it at all — NAT, firewalls, VPNs, and the cryptography quietly holding all of it together.

⏱ 20–25 min read 📋 Prerequisites: Chapters 4, 6 & 7 📍 Chapter 11 of 12

NAT: stretching a scarce resource into a side effect of security

Chapter 4 introduced private address ranges like 192.168.1.x — usable behind your own router, but not routable on the public Internet. NAT (Network Address Translation) is what makes that usable at all: your router rewrites the source IP (and port) of every outgoing packet to its own public IP, keeps a translation table remembering which internal device made which request, and rewrites replies back to the correct private address on the way in.

Inside your networkOn the public Internet
192.168.1.5:51000203.0.113.9:40001
192.168.1.7:51000203.0.113.9:40002

Notice what that table implies: an unsolicited inbound packet that doesn't match any existing entry has nowhere to go and gets dropped by default. That wasn't NAT's original goal — it was invented purely to stretch a shrinking pool of IPv4 addresses — but as a side effect, every device behind a home router is already unreachable from the outside unless it spoke first. NAT ended up being one of the most widely deployed security boundaries on Earth almost by accident.

🧪 Try it yourself: watch NAT rewrite a packet

On a Linux box acting as a router (adjust interface names for your setup):

sudo iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
sudo tcpdump -i eth0 -n

Send traffic from a device behind it and watch the source IP in the capture — it's the router's public address, never the private one that actually sent it. That single rewritten field is the entirety of NAT.

Firewalls: deciding what's allowed to pass at all

A firewall is a checkpoint that inspects traffic and decides, by rule, what gets through. The simplest kind — packet filtering — checks each packet in isolation against a list of allow/deny rules based on IP and port. Stateful firewalls go further, tracking which connections you actually initiated and automatically allowing their replies back in — which is precisely the same bookkeeping idea behind NAT's translation table, just applied as policy instead of address rewriting. Application-layer firewalls go further still, inspecting the actual content of allowed traffic (like an HTTP request) rather than just its headers.

TypeInspectsExample decision
Packet filterIP, port, protocol"Block anything to port 23"
StatefulConnection state"Only allow replies to connections we started"
Application-layerActual request content"Block this HTTP request — it looks like an attack"
🧪 Try it yourself: block a port, then let it back in
# Block inbound SSH:
sudo iptables -A INPUT -p tcp --dport 22 -j DROP

# Confirm it's actually blocked from another machine, then undo it:
sudo iptables -D INPUT -p tcp --dport 22 -j DROP

Run this only on a machine you have another way to reach — a firewall rule that blocks your only way in is a lesson best learned on a disposable virtual machine, not a server you need later today.

VPNs: an encrypted tunnel across a network you don't trust

A VPN (Virtual Private Network) wraps your traffic in an encrypted tunnel to a trusted endpoint before it touches the network in between. Anyone watching the path your packets actually take — a coffee shop's router, an ISP — sees only encrypted tunnel traffic to that one endpoint; your real destination and the content of your traffic are both hidden inside it. Common implementations include IPSec, OpenVPN, and WireGuard, used both to connect remote workers into a private company network and, more generally, to keep traffic private on networks you don't control.

🚚 Analogy: a VPN is an armored car on a public road

Anyone standing on the highway can see an armored truck driving past — the road is public, and so is the fact that a truck is using it. What they can't see is what's inside the truck, because it's sealed until it reaches its destination. A VPN does exactly that to your traffic: the Internet path in between is still visible as "encrypted traffic heading to a VPN server," but the contents and the real destination stay sealed until they reach the other end of the tunnel.

Encryption primitives: the math actually doing the locking

Chapter 6 walked through the TLS handshake without dwelling on the cryptography underneath it. Here's the part that was doing the actual locking:

  • Symmetric encryption (like AES) uses one shared key to both encrypt and decrypt. It's fast — fast enough to encrypt a video stream in real time — but both sides need the same secret key already, which raises an obvious problem: how do two strangers agree on a secret key over a connection that isn't secure yet?
  • Asymmetric encryption (like RSA or elliptic-curve Diffie-Hellman) solves exactly that problem with two mathematically linked keys — a public one anyone can use to encrypt (or verify a signature), and a private one only its owner holds, needed to decrypt (or sign). It's what makes the TLS key exchange from Chapter 6 possible in the first place: two strangers, no shared secret yet, agreeing on one over a channel someone might be listening to.
  • Hashing (like SHA-256) takes any input and produces a fixed-length fingerprint that's practically impossible to reverse or fake a match for — used to verify a file wasn't tampered with, to store passwords without keeping the actual password, and to fingerprint certificates.
📪 Analogy: two very different kinds of lock

Symmetric encryption is an ordinary lockbox — one key both locks and unlocks it, so you'd better already have a safe way to get a copy of that key to the other person. Asymmetric encryption is a mail slot: anyone on the street can drop a letter through the public slot (encrypt with the public key), but only the person holding the private key to the box behind it can ever take mail back out (decrypt). TLS uses the mail slot briefly, just to agree on a lockbox key — then switches to the lockbox for everything else, because it's so much faster.

⚡ Did you know?

That switch isn't a stylistic choice — it's forced by raw performance. Asymmetric algorithms like RSA are commonly on the order of 100 to 1,000 times slower than symmetric algorithms like AES for the same amount of data. That's precisely why every TLS connection uses asymmetric cryptography for only a few milliseconds — just long enough to safely agree on a symmetric key — and then hands every remaining byte of your video call, download, or web page off to the much faster symmetric cipher for the rest of the conversation.

🧪 Try it yourself: run all three primitives from the command line
# Symmetric: encrypt a file with AES
openssl enc -aes-256-cbc -in secret.txt -out secret.enc

# Asymmetric: generate a public/private key pair
ssh-keygen -t ed25519 -f demo_key

# Hashing: fingerprint a file
sha256sum secret.txt

Three completely different mathematical tools, each solving a different piece of the same overall problem — and together, they're the entire cryptographic foundation this whole site's HTTPS padlocks have quietly depended on since Chapter 6.
