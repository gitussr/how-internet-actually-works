Chapter 7 · Where Requests Actually Get Answered

Servers & Data Centers

Every protocol in Chapter 6 assumes something is listening on the other end. This chapter is what that something actually is — a process bound to a port, backed by a database, standing behind a load balancer, sitting in a building full of machines much like your own.

⏱ 20–25 min read 📋 Prerequisites: Chapter 6 📍 Chapter 7 of 12

What "a server" actually is

Strip away the mystique and a server is nothing exotic: it's a normal computer, running a normal operating system, with one process bound to a port and listening for incoming TCP connections — exactly the sockets introduced back in Chapter 5, just running continuously instead of for one request. When your browser connects to port 443 on some IP address, there's a specific piece of software — commonly Nginx or Apache for web traffic — sitting there, accepting the connection and deciding what to do with it.

"The cloud" doesn't change this. It's a real building with real racks of real machines somewhere on Earth; the "cloud" part is just that someone else owns and operates the hardware, and rents you the ability to run your own process on it. Nothing about a server, physically, is different from the laptop you're reading this on — it's the same idea, just left running, in a room built for exactly that.

🧪 Try it yourself: be the server for five minutes
# Start a real, working web server on your own machine:
python3 -m http.server 8000

# In another terminal, connect to it like a browser would:
curl http://localhost:8000

# And see the process actually listening on that port:
ss -tulnp | grep 8000

That's the entire concept behind every website you've ever visited — scaled up, hardened, and usually running something more sophisticated than Python's built-in server, but doing exactly this at its core.

Databases: where the state actually lives

A web server on its own tends to be stateless — it doesn't remember you between requests. The actual data behind a request — your account, your order history, a social media feed — lives in a database, queried fresh each time. Most of what a web server "does" is really: accept a request, ask a database a question, format the answer as HTML or JSON, send it back.

Databases split broadly into two families: SQL (relational) databases like PostgreSQL and MySQL, which store data in strictly structured tables with defined relationships between them, and NoSQL databases like MongoDB or Redis, which trade that structure for flexibility or raw speed — useful when data doesn't fit neatly into rows and columns, or when you need answers in microseconds.

🧪 Try it yourself: run a real query from the command line
sqlite3 example.db
sqlite> .tables
sqlite> SELECT * FROM users LIMIT 5;

Every "load a profile page" or "show my recent orders" request you've ever triggered on the web reduces, somewhere on a server you never see, to a query that looks almost exactly like this one.

From one server to a data center

A real service never runs on one machine. Popular sites handle far more simultaneous requests than any single computer could process, and a single machine is also a single point of failure — if it goes down, so does the entire service. Data centers solve both problems by housing thousands of servers together with redundant power, cooling, and networking, and virtualization lets a cloud provider slice each physical machine into many independent virtual servers rented out to different customers, all sharing hardware none of them can see.

⚡ Did you know?

The data center industry actually grades facilities on how much downtime they're designed to tolerate. The Uptime Institute's highest grade, Tier IV, requires every single piece of power and cooling infrastructure to be fully duplicated — so that even a complete failure of one path, or planned maintenance on it, never takes the facility offline. The target: no more than about 26 minutes of downtime in an entire year.

VPCs: your own private slice of someone else's data center

When you rent capacity from a cloud provider, you don't just get bare virtual machines — you get a VPC (Virtual Private Cloud): a logically isolated network, entirely yours to define, that behaves almost exactly like a traditional data-center network even though it's carved out of shared physical infrastructure. You choose the IP address ranges, split them into subnets, and decide which subnets can reach the public Internet at all.

  • Internet Gatewaythe VPC's front door to the public Internetedge
  • Public subnetload balancers, anything meant to be reachableexposed
  • Private subnetapp servers, databases — no direct Internet accessshielded
  • Availability Zone A / Bthe same setup duplicated in a separate physical facilityredundant

That split between public and private subnets is a deliberate security boundary, not just an organizational habit: a database sitting in a private subnet is simply unreachable from the open Internet no matter what credentials an attacker has, because there's no network path to it at all — the strongest kind of protection is often just not being reachable in the first place. Chapter 11 covers the firewalls and NAT that make subnets like this actually work.

Load balancers: the traffic cop

With multiple identical servers running behind the scenes, something has to decide which one handles each incoming request — that's a load balancer. It sits in front of a pool of servers, accepts connections on their behalf, and distributes them across the pool so no single machine gets overwhelmed and, just as importantly, so traffic keeps flowing seamlessly even if one server in the pool goes down entirely.

🛒 Analogy: a load balancer is a grocery store manager

Walk into a grocery store with ten checkout lanes and no one directing traffic, and everyone crowds into whichever lane looks shortest at a glance — usually wrong. A store manager standing at the entrance, actively sending each new customer to the shortest actual line, gets everyone through faster and keeps any one cashier from getting buried. That's precisely a load balancer's job, applied to web requests instead of shopping carts.

Load balancers operate at different layers of the stack: a Layer 4 load balancer only looks at IP addresses and ports — fast, but blind to what's actually inside the request. A Layer 7 load balancer reads the HTTP request itself, which means it can make smarter decisions, like routing /api/* requests to one pool of servers and /images/* to an entirely different one optimized for serving static files.

AlgorithmHow it decides
Round robinCycles through servers in order, one request each
Least connectionsSends the request to whichever server currently has the fewest active connections
IP hashAlways routes the same client IP to the same server — useful when a server needs to remember you
