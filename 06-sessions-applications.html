Chapter 6 · Where the Internet Starts Looking Familiar

Sessions & Applications

TCP hands you a reliable pipe and nothing else — it has no idea whether the bytes flowing through it are a web page, a password, or a chat message. HTTP, TLS, DNS, SSH, and email are the agreements that turn that pipe into something you'd actually recognize as the Internet.

25–30 min read Prerequisites: Chapter 5 Chapter 6 of 12

One pipe, many languages

Everything in this chapter runs on top of the TCP or UDP connections Chapter 5 built. None of it changes how packets travel — it's all just agreed-upon patterns of bytes sent back and forth over a connection that already exists. A web browser and a mail client use the exact same kind of TCP socket; the only difference is which words they've agreed to say to each other once it's open.

HTTP: the web's request-response protocol

HTTP is about as simple as protocols get: a client sends a plain-text request, a server sends back a plain-text response, and the connection can be reused or closed. A real request looks close to this: 

GET /index.html HTTP/1.1
Host: example.com
User-Agent: curl/8.4.0
Accept: */*

and the response:

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1256

<html>...</html>

That's it — a method (GET, POST, and others), a path, some headers, and optionally a body. The problem is that every byte of this is sent in the clear. Anyone positioned between you and the server — a coffee shop's Wi-Fi router, an ISP, anyone on the same network — can read it, including passwords typed into an unencrypted login form. HTTPS is the fix: it's the exact same HTTP conversation, just wrapped inside an encrypted tunnel before it starts, over port 443 instead of port 80.

TLS: the handshake that makes HTTPS secure

That encrypted tunnel is built by TLS (Transport Layer Security), and it has three jobs at once: keep the conversation private (confidentiality), detect if it's been tampered with (integrity), and prove the server is actually who it claims to be (authentication). Simplified, the handshake goes:

  • Client Hello"here's what encryption I support"1
  • Server Hello + Certificate"here's what we'll use, and proof of who I am"2
  • Key exchangeboth sides derive the same secret session key3
  • Encrypted session beginseverything from here is unreadable to anyone else4

The server's identity check relies on a certificate — signed by a Certificate Authority your browser already trusts — which is why a browser warns you loudly when a certificate doesn't check out instead of failing silently. And modern TLS almost always uses a fresh, temporary key for every single connection (ephemeral key exchange), which means even if a server's long-term private key were ever stolen, past conversations that already happened can't be decrypted retroactively — a property called forward secrecy.

Analogy: TLS is checking ID before whispering

Meeting a stranger to exchange something sensitive, you'd check their ID against something you already trust before agreeing on a private code language to use between yourselves for the rest of the conversation. That's the TLS handshake exactly: verify identity first (the certificate), then agree on a shared secret (the key exchange), then switch to that private language (symmetric encryption) for everything else.

Try it yourself: watch a TLS handshake and inspect a certificate
openssl s_client -connect example.com:443

You'll see the negotiated protocol version, the cipher chosen, and the full certificate chain right in the terminal. Compare it against: 

curl -v http://example.com   # watch headers fly by in plain text
curl -v https://example.com  # same request, now wrapped in TLS

SSH: the same trust model, for logging in remotely

SSH (Secure Shell) applies a similar idea to remote logins: it cryptographically verifies the server's identity (your terminal's warning about "the authenticity of host X can't be established" is SSH asking you to trust a new server's fingerprint), negotiates an encrypted channel, and then authenticates you — usually via a password or, far more securely, a public/private key pair where the private key never leaves your machine. Once established, that one encrypted channel can carry a remote shell, forward other ports, or transfer files (SFTP) — all inside the same connection.

WebSockets: turning a request into a standing conversation

HTTP was built for short request-response exchanges, but some applications — chat, live dashboards, multiplayer games — need a channel that stays open and can send data in either direction at any time. WebSockets get there with a clever trick: the connection starts as an ordinary HTTP request carrying an Upgrade: websocket header. If the server agrees, it responds 101 Switching Protocols, and from that point on the exact same TCP connection stops speaking HTTP and becomes a raw, full-duplex channel — no more request/response, just data flowing whenever either side wants to send it.

DNS: turning names into addresses

Every protocol so far assumes you already have an IP address to connect to. DNS is what gets you there from a name like example.com. It's organized as a hierarchy — a root, then top-level domains (.com, .org), then the authoritative server for the specific domain — and a recursive resolver (often run by your ISP, or a public one like 8.8.8.8) walks that hierarchy on your behalf so your device doesn't have to, caching answers along the way so the same lookup doesn't have to happen twice.

Did you know?

There are only 13 named DNS root server addresses in the entire world — a limit baked into how the original root hint responses were sized. But that number is deceptive: nearly every one of those 13 names actually corresponds to hundreds of physical servers scattered across the globe, all sharing the same address via a routing technique called anycast (Chapter 12), where the network itself sends your query to whichever copy happens to be nearest. The "13 root servers" that hold up the entire domain name system are, in reality, over a thousand machines wearing 13 name tags.

Try it yourself: walk the DNS hierarchy by hand
dig +trace example.com

This deliberately skips your resolver's shortcuts and performs the full walk itself — root, then .com's servers, then example.com's own authoritative servers — printing every hop. It's the same hierarchy described above, made visible one query at a time.

SMTP: the postal service for email

Sending email uses SMTP (Simple Mail Transfer Protocol) — a push protocol, where your mail server actively hands the message off to the recipient's mail server, often hopping through several intermediate servers along the way, much like a letter passing through multiple sorting facilities. Retrieving mail is a separate problem, handled by different protocols entirely (IMAP or POP), which is why "sending" and "receiving" email genuinely run on different machinery under the hood, even though your inbox makes them look like one continuous experience.

What's next

We now have the full request-to-response journey covered — from an electron to a rendered web page. But none of these protocols run themselves: something has to actually listen on port 443, hold a database, and balance load across thousands of simultaneous requests. Chapter 7 goes behind the application layer into the servers, databases, and cloud infrastructure that answer every request this chapter described.
