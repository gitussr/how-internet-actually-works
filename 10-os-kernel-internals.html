Chapter 10 · What Happens the Instant a Packet Arrives

OS & Kernel Internals

Every chapter so far has quietly assumed a packet "arrives" at a program. This is the missing step: how the operating system catches it, wakes up the right process, and hands it over — for every packet, on every connection, without melting the CPU.

20–25 min read Prerequisites: Chapters 5 & 7 Chapter 10 of 12

The socket: where the network meets your code

Chapter 5 introduced the socket as a concept — an IP address plus a port. To the operating system, a socket is also a very concrete thing: a handle your program gets back from the kernel, which behaves almost exactly like an open file. A server calls socket() to create one, bind() to claim a specific port, listen() to mark it ready for incoming connections, and accept() to receive the next one — which blocks, doing nothing, until a client actually shows up. 

// Server, in skeleton form:
socket()   // create a handle
bind()     // claim port 443
listen()   // "I'm open for connections"
accept()   // block here until someone connects
read()     // block here until they send data
write()    // send a response back

That's genuinely almost the entire API. Every web server, database, and SSH daemon on Earth is, underneath layers of application logic, calling these same handful of functions.

What actually happens when a packet arrives

Here's the walk this entire site has been building toward, run backwards in microseconds, inside the kernel, for every single packet:

  • NIC receives signalelectrical/optical/radio pulses, per Chapter 2hw
  • Interrupt (or NAPI poll)NIC tells the CPU a packet is waitinghw→sw
  • Kernel network stackstrips link, IP, then TCP/UDP headerskernel
  • Socket receive bufferpayload lands, matched to the right socketkernel
  • Your process wakes upblocked read()/accept() call finally returnsapp

Notice what that middle step is actually doing: it's unwrapping Chapters 3 through 6 in reverse, one header at a time, to figure out exactly which of possibly thousands of sockets on the machine this particular packet belongs to.

Analogy: sockets are mailboxes, the kernel is the sorting room

A large apartment building has one mail slot where the postal carrier drops everything, and a back room where mail actually gets sorted into individual tenants' mailboxes based on the name and unit number on each envelope. The kernel is that sorting room: every packet arrives at the same physical NIC, and the kernel reads its headers — the "name and unit number" — to route it into the correct socket's buffer. Your program is a tenant who only ever checks its own mailbox, with no idea how much other mail passed through that same building.

Interrupts vs. polling: two ways to notice a packet arrived

The classic approach is a hardware interrupt: the NIC physically signals the CPU the instant a packet lands, which drops whatever it was doing to handle it. That's fine at low traffic, but under heavy load — tens of thousands of packets per second — the constant interrupting can consume more CPU than actually processing the data. Linux's answer is NAPI: under high load, the kernel switches to periodically polling the NIC for a batch of packets instead of being interrupted for every single one, trading a sliver of latency for a large reduction in overhead — the exact same batching trade-off that shows up everywhere from TCP's delayed ACKs to disk I/O scheduling.

epoll: waiting on thousands of connections with one thread

A busy server might hold ten thousand connections open at once. Spinning up a thread to sit and block on read() for each one doesn't scale — that's ten thousand threads mostly doing nothing. epoll (Linux; kqueue on BSD/macOS) solves this by flipping the question: instead of asking each socket "do you have data?" one at a time, a single thread tells the kernel "wake me up when any of these ten thousand sockets has something ready," then goes to sleep until the kernel taps it on the shoulder. Older approaches like select() and poll() technically offer the same idea, but have to rescan the entire list of sockets every single call — fine for a handful of connections, ruinous at ten thousand.

MechanismScales toHow it checks readiness
select() / poll()Hundreds of connectionsRescans the full list every call
epoll / kqueueHundreds of thousandsKernel pushes only what's ready
Try it yourself: be both ends of a socket

Save and run this as the server:

import socket
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.bind(("0.0.0.0", 9000))
s.listen(1)
conn, addr = s.accept()      # blocks until a client connects
print("connected from", addr)
data = conn.recv(1024)
conn.sendall(data)           # echo it straight back

Then, in another terminal, the client:

import socket
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.connect(("127.0.0.1", 9000))
s.sendall(b"hello kernel")
print(s.recv(1024))

Every function call in both snippets maps directly onto the skeleton from the start of this chapter — you've just watched accept() unblock in real time.

Watching packets happen, in real time

Every Wireshark or tcpdump capture used throughout this site works the same way: it asks the kernel for a raw, filtered copy of packets as they pass through, using a small, fast in-kernel filtering language called BPF (Berkeley Packet Filter) to discard anything that doesn't match, so userspace only ever sees the packets you actually asked for. 

sudo tcpdump -i any 'tcp port 443' -c 5

That quoted expression is compiled straight into a tiny BPF program and run inside the kernel, packet by packet — filtering happens before your terminal ever sees a single byte.

eBPF: running your own code inside the kernel

Classic BPF could only filter packets. eBPF (extended BPF) generalizes the same idea into a way to attach small, custom programs directly to almost any point in the kernel — network events, system calls, even individual function calls — without writing a kernel module or recompiling anything. 

bpftrace -e 'kprobe:tcp_v4_connect { printf("connect from PID %d\n", pid); }'

That one line logs, live, every process on the machine the instant it opens a new TCP connection — the same tcp_v4_connect kernel function this chapter's whole packet-arrival walk eventually runs through.

Did you know?

Letting arbitrary code run inside the kernel sounds like a security nightmare — a bad kernel module can crash or compromise the entire machine. eBPF's answer is a built-in verifier: before any eBPF program is allowed to load, the kernel statically proves it cannot crash, cannot loop forever, and cannot read memory it isn't allowed to touch — and rejects it outright if it can't prove that. It's one of the few places in a modern OS where untrusted-looking code gets to run at the very core of the system, backed not by trust in the code, but by a mathematical proof the kernel insists on first.

What's next

We now know exactly how a packet gets from a wire into a program's hands. But arriving isn't the same as arriving safely — nothing covered so far stops an unwanted connection from reaching that same socket, or another party from reading the data along the way. Chapter 11 covers NAT, firewalls, VPNs, and the encryption primitives that keep all of this from being an open book.
